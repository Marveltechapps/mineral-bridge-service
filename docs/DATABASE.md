# Database

MongoDB 7 (replica set — transactions are required), Mongoose 8. All timestamps are UTC `Date`s. Every
document also carries Mongoose `_id`, and almost every collection has a **human id** (`orderId`,
`lotId`, `kycId` …) that is the identifier the APIs expose.

## 1. Two groups of collections

| Group | Collections | Owner |
|---|---|---|
| **Admin console** | everything prefixed `adm_*` (below), plus the staff collections `staffusers`, `staffsessions` | `src/modules/admin/**`, `src/modules/staff`, `src/modules/sessions` |
| **Customer apps** (mobile + web) | `users`, `orders`, `auctions`, `bids`, `notifications`, `carts`, `products`, `kycs` … | `src/modules/*` and `src/models/*.model.ts` |

> **Known integration gap.** The admin models are deliberately namespaced (`Adm<Name>` on `adm_<collection>`)
> because the customer modules already own collections with the same natural names (`users`, `orders`,
> `auctions`, `bids`, `kyc`) but with different shapes (mobile/web store integer minor units keyed by
> `userId` ObjectIds; the console stores human ids). Until an adapter is written the two worlds are **not
> shared**: an order placed in the mobile app does not appear in the admin console, and vice-versa. The
> adapters belong in `src/app-clients/shared/*.adapter.ts` (admin ⇄ customer write-through or a one-off
> backfill). Everything the admin API *does* touch (KYC decisions, tier changes, offers, settlements,
> disputes …) is fully persisted and audited in the `adm_*` collections.

## 3. Relationships

```
StaffUser (publicId STF-…) ──< StaffSession
Role (roleId ROLE-…) ── embedded copy in StaffUser.role / permissions   (settings #130 re-syncs staff)
User (userId USR-…) ──< TierRequest ──(approve)──> KycSubmission ──< KycDocument
                    ──< Order (counterpartyId) ──< Offer, stageLog[], exceptions[]
                    ──< Ticket ──< notes[]            ──< Call (phone/userId)
                    ──< Dispute (partyId, linked → order|lot|lc|…)  ──(resolution)──> Settlement
                    ──< OutboundMessage
VaultLot (lotId MBV-…) ──< Listing, Auction ──< Bid, AuctionEvent (SSE)
                       ──< Passport ──> Anchor (merkle batch)  ·  ChainEvent
Negotiation (NEG-…) ──> Contract (CTR-…) ──> LetterOfCredit (LC-…) ──> Settlement (seller_payout)
Rate ──< RateHistory
CourseCategory ──< Course ──< Lesson          Enrolment (userId × courseId)
Banner · Partner (carrier/hub/lab referenced by Order.carrierId/hubId/labId)
AuditLog  — append-only, references any record by {type,id}
ActivityEvent — the dashboard feed, written together with the audit row
SettingsDoc — one doc per key: roles | platform | btc (version → ETag)
Counter — atomic sequences behind every human id
```

Foreign keys are stored as **human ids** (strings), not `ObjectId`s, so records can be deep-linked
(`{type,id}` refs) and exported without joins.

## 4. Money storage

* Persisted money is **integer minor units**: `{ amountMinor: Number, currency, scale }`
  (`USD`/`KES` scale 2, `BTC` scale 8). Unit prices add `per` (`kg|t|g|oz`); quantities are `{ value, unit }`.
* **Never** store or compute with floats or major units. All conversion goes through
  `src/modules/admin/shared/money.ts` (`parseMoney`, `outMoney`, `priceTimesQuantity`, `addStored`).
* The **admin wire format is decimal major units** (`{ amount: 15350000, currency: 'USD' }`), mobile/web use
  minor units. Inbound admin amounts with more decimals than the currency allows are rejected with
  `422 validation/failed` — money is never silently rounded.
* `Settlement.usdEquivalent` stores the USD value (with the rate/time used) for cross-currency rows so reports
  can aggregate without joining the rate table. Aggregations use `amountMinor` sums, never `$toDouble` maths
  on major units.
* BTC amounts use scale 8 (satoshis). `Country.btc.limit` is a normal money sub-document.

## 5. Concurrency and integrity rules

| Concern | Mechanism |
|---|---|
| Human ids | `Counter` (`findOneAndUpdate $inc`, upsert) → `nextId('lot')` = `MBV-2026-0401` |
| Multi-document writes | `withTx(session => …)`; the audit row and activity event are written in the **same** transaction as the change |
| Stale writes | conditional `findOneAndUpdate({ …, status })` → `409 conflict/stale-state` |
| Edit-gated resources | `__v` + weak ETag (`W/"…"`); `If-Match` mismatch → `412 conflict/etag-mismatch` |
| Duplicate submits | `Idempotency-Key` + unique `scope` index; `required` on #52, #72, #106 |
| Four-eyes | `createdBy`/`preparedBy` fields compared with the acting staff id → `403 auth/four-eyes` |
| One pending tier request per user | partial unique index on `adm_tier_requests` |
| Audit | `AuditLog` rejects `update*`, `delete*` and re-`save` (append-only); retention 7 years |

## 6. Initialization

The API process inserts missing defaults before it listens (`src/bootstrap/initialize-database.ts`).
`npm run seed` calls that same function and is not part of a normal start.

Reference data (categories, minerals, units, countries with BTC regulation, banks), the role matrix,
and platform/auth settings are created when their keys are absent. Existing documents are not
updated and passwords are not reset. Sample rates, the academy tour, and sample catalogue lots are
inserted only for an empty local development database. Production and remote databases do not
receive those rows or the development admin password. A customer row is created only when
`SEED_USER_EMAIL` and `SEED_USER_PASSWORD` are both set and the database is local development.
